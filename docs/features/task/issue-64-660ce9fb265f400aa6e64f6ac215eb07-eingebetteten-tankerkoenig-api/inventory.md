# Bestandsaufnahme: GitHub-Release-Ablage entfernen, Auslieferung nur über den App Store (Issue #64)

Analysiert wurde die CI-/Release-Ebene des Repositories (GitHub-Actions-Workflows, Composite Actions, CI-Hilfsskripte, der Build-Zeit-Schlüsselmechanismus des Tankerkönig-API-Schlüssels sowie die zugehörige Dokumentation) bezogen auf die Anforderung, die Ablage der Releases auf GitHub zu entfernen und die App ausschließlich über App Store Connect (TestFlight) auszuliefern. Es sind keine Anwendungsklassen (Datenmodell, Services, UI) von Änderungen betroffen.

## Zusammenfassung

- **Zwei Workflows erzeugen heute GitHub-Releases:** `release.yml` (Push → `main` oder Tag `v*.*.*`) legt per `gh release create`/`gh release upload` die Assets `release-win-x64.zip` + `update.json` ab und enthält einen Reparaturpfad für unvollständige Releases; `staging-ci.yml` legt je RC ein GitHub-**Pre-Release** an (`gh release create --prerelease`, Zeile 405–414). Kein weiterer Workflow nutzt `gh release` oder lädt Release-Assets hoch.
- **Release- und RC-Tags entstehen heute nur implizit durch `gh release create`** — es gibt keinen einzigen `git tag`-/`git push`-Schritt in den Workflows. Die Versionsermittlung (`scripts/determine-next-version.mjs`, `git tag --merged HEAD --list "v*"` bzw. `git tag --list "v<ver>-rc.*"`) hängt vollständig an diesen Git-Tags: Ohne Tag-Erzeugung würde jeder Lauf dieselbe Version erneut versuchen.
- **`scripts/resolve-release-version.mjs` ist der einzige GitHub-Releases-Consumer im Skriptbestand:** `ghGetRelease`/`ghListReleases` (per `gh api`), `EXPECTED_ASSETS` und der `release_action: "upload-existing"`-Reparaturpfad prüfen Release-Existenz und Asset-Vollständigkeit.
- **`update.json` hat keinen Consumer:** Die Download-URL zeigt auf `releases/download/…`; im App-Code existiert kein Auto-Updater und keine Referenz auf `update.json` oder `releases/download` (Grep über `src/` ohne Treffer). Es ist ein veröffentlichtes, aber von nichts gelesenes Manifest.
- **iOS ist bereits der einzige signierte Auslieferungspfad:** `.github/actions/package-ios` baut signiert (bei `IOS_SIGNING_ENABLED='true'` + vollständigen Secrets), validiert die `.ipa` und lädt per iTMSTransporter nach App Store Connect/TestFlight — in `release.yml`, `staging-ci.yml` und als reine Compile-Prüfung in `pr-staging-ci.yml`. Fällt die Signierung weg, gibt es **keinen Fehlschlag**, sondern still einen unsignierten Simulator-Build — ohne GitHub-Release gäbe es dann Releases ohne jedes Auslieferungsergebnis.
- **Der Tankerkönig-API-Schlüssel ist heute nur im iOS-Binary eingebettet:** `TankerkoenigApiKey.targets` schreibt ihn als `AssemblyMetadata("TankerkoenigApiKey", …)` für alle Zielframeworks in die Assembly; nur der iOS-Build erhält das Secret `FUEL_PRICE_API_KEY`. Das Windows-Paket wird explizit ohne Schlüssel gebaut (geleerte Umgebung, versteckte props-Datei) — abgesichert durch `validate-workflows.py`. Der Rotationsweg existiert schon: `ApiKeyProvider` überschreibt die Geräteablage bei abweichendem Build-Schlüssel.
- **Aktueller Bestand auf GitHub:** 48 Releases (Stabile + Pre-Releases, zuletzt `v0.10.0`/`v0.11.0-rc.1`), jeweils mit den Assets `release-win-x64.zip` + `update.json`; 50 Git-Tags `v*` (12 stabile `v0.1.0`–`v0.10.0`). Repository ist **öffentlich**, Default-Branch `main`.
- **`validate-workflows.py` enthält Release-spezifische Regeln:** Parsen der Asset-Argumente von `gh release create/upload` (`gh_release_assets`, `check_release_commands`) inkl. Positivliste — die im Test `test_validate_workflows.py` die aktuellen Aufrufe explizit als erlaubt einträgt (`test_current_release_commands_are_allowed`).
- **Dokumentationsstellen identifiziert:** `docs/help/ci-cd/` (README „Release-Artefakte", workflows.md, einrichtung.md, versionierung.md), `docs/help/Preisdaten/api-schluessel.md` (Artefakt-Tabelle + bereits vorhandener Sicherheitshinweis inkl. Rotationshinweis), `docs/RELEASE_NOTES.md`, `changes.log`. ADR-Konvention: `docs/adr/NNNN-titel.md` mit Status/Kontext/Entscheidungen/Folgen; nächste Nummer **0023** (letzter: 0022). `pages/` verlinkt nur den Quellcode, keine Downloads — unberührt.

Test-Ausgangszustand: Alle ausgeführten Suiten sind **grün, ohne bekannte Fehlschläge** — `npm test` 32/32, `test_validate_workflows.py` 14/14, `validate-workflows.py` Exit 0 (11 Workflows), iOS-Deployment-Skriptprüfung vollständig OK, Build 0 Warnungen/0 Fehler, Unit 2155/2155, Integration 199/199, E2E (blockierende Lane) 2/2, Formatprüfung ohne Verstoß. Details und Nachweise: [Tests](inventory/tests.md).
